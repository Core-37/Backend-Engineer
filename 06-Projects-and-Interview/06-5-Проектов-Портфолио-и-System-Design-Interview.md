# 🚀🏆 06. Пять Сильных Системных Проектов для GitHub & Алгоритм System Design Interview

> Обычные CRUD-проекты («блог» или «To-Do лист») больше не выделяют на собеседованиях уровня Middle+/Senior Backend Systems Engineer. Ниже — **5 проектов, которые доказывают системное мышление**, и чёткий 45-минутный каркас для любого **System Design Interview**.

---

## 🛠️ 1. Пять Системных Проектов на GitHub (на Go, Rust или Python)

1. **Мини-Redis / Встраиваемое Key-Value Хранилище с WAL и TTL:**
   - Реализуй TCP-сервер (протокол RESP или свой бинарный протокол), хранение в памяти с `RWMutex` или `Sharded Map` (снижение Lock Contention!), **Write-Ahead Log (`WAL`)** с `fsync` для восстановления после краша и фоновую очистку протухших ключей (TTL).
   - *Покажи в README:* бенчмарк пропускной способности (`RPS`, `p99`), тест восстановления после `kill -9`! *(Стартовая база — наша Лаба №2).*

2. **Высоконагруженный Distributed Rate Limiter & API Gateway Proxy:**
   - Реверс-прокси (на Go/Rust), который реализует **Token Bucket** / **Sliding Window** на Redis (через атомарный Lua-скрипт!), добавляет `Circuit Breaker`, `Timeouts`, структурные JSON-логи с `trace_id` и метрики Prometheus.
   - *Покажи в README:* нагрузочный тест `wrk / k6` и график на Grafana! *(Стартовая база — Лабы №1 и №3).*

3. **Надёжный Платёжный / Заказной Сервис с `Transactional Outbox` и `Idempotency`:**
   - Сервис на PostgreSQL + Kafka (в `docker-compose`): при оплате сохраняет транзакцию + запись в таблицу `outbox` в **1 ACID-транзакции**, отдельный воркер доставляет события в Kafka, а API защищено через `Idempotency-Key` и `SELECT FOR UPDATE` (без двойных списаний при параллельных запросах!).

4. **Распределённый Планировщик Задач (Job Scheduler) или Raft-кластер (по MIT 6.5840):**
   - Кластер из 3–5 узлов с выбором лидера (либо через Raft, либо через lease в `etcd`/Postgres `SKIP LOCKED`), автоматическим перезапуском зависших воркеров (heartbeat + timeout) и шардированием через **Consistent Hashing**.

5. **Высокопроизводительный TCP Load Balancer (L4/L7) с Health Checks & Graceful Shutdown:**
   - Принимает входящие соединения, распределяет их по бэкендам (Round Robin / Least Connections), регулярно проверяет здоровье нод, корректно отключает упавшие и держит `Graceful Shutdown` по `SIGTERM` без единой ошибки `502` во время нагрузки!

## 🎯 2. Универсальный Алгоритм Прохождения System Design Interview за 45 Минут

Не бросайся рисовать «микросервисы и Kafka» на 1-й минуте! Иди строго по этим **4 шагам**:

### Шаг 1. Проясни требования и ограничения (5–7 минут)
- **Функциональные (Что делает система?):** 3–4 главные фичи (например, для URL Shortener: создать короткую ссылку, сделать редирект, посчитать переходы).
- **Нефункциональные (Самое важное для Systems Engineer!):**
  - Какая аудитория (DAU) и нагрузка (**RPS чтения vs RPS записи**)?
  - Целевая задержка (**Latency**, напр. `p99 < 50 мс`)?
  - Что важнее по CAP при сбое сети: **Consistency** (деньги/бронь билетов) или **Availability** (лента/сокращатель ссылок)?
  - Сколько лет храним данные?

### Шаг 2. Расчёт объёмов и узких мест (Back-of-the-Envelope Estimation, 5 минут)
- Посчитай **Average RPS** и **Peak RPS** (`× 3..5`).
- Посчитай **Storage** (объём данных на 1–5 лет) и **RAM для кэша** (правило 80/20: 20% горячих данных).
- Сразу вслух заметь: *«У нас 100,000 RPS на чтение и 5 ТБ данных — один инстанс Postgres не выдержит ни по сети, ни по диску, значит нужны Read Replicas + Redis + Sharding»*.

### Шаг 3. Высокоуровневая архитектура (10–15 минут)
Нарисуй чистый **путь запроса сверху вниз**:
- Клиент ➔ CDN ➔ L4/L7 Load Balancer (Rate Limiter) ➔ Stateless API-сервисы ➔ Кэш (Redis) + База данных (SQL/NoSQL) + Асинхронная очередь (Kafka + Workers).
- Обязательно пропиши **схему таблиц/ключей БД** и контракты API!

### Шаг 4. Глубокое погружение и поиск поломок (Deep Dive, 15–20 минут)
Сам покажи, где твоя система может сломаться, и реши это на уровне «железа и кода»:
1. **Шардирование и горячий ключ:** по какому полю шардим (`user_id`? `hash`? Consistent Hashing?) и что делать, если у 1 блогера 50 млн подписчиков (*Celebrity Problem*)?
2. **Отказы БД и сети:** что будет при падении мастера БД? Как избежать потери сообщений (*Transactional Outbox*) и дублей (*Idempotency*)?
3. **Кэш:** как защититься от *Cache Stampede* (`Singleflight`) и *Cache Penetration* (`Bloom Filter`)?
4. **Наблюдаемость:** какие метрики (`p99`, lag репликации, consumer lag в Kafka) выводим в Grafana?
