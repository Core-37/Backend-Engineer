## 🩺 1. Метод Брендана Грегга: Диагностика Linux-сервера за 60 секунд

Когда продакшн начал тормозить, выполни ровно эти **10 команд сверху вниз**:

| Шаг | Команда | На что смотреть (Красный флаг) |
| :---: | :--- | :--- |
| **1** | `uptime` | Load Average за 1/5/15 мин. Если выше числа ядер CPU — задачи стоят в очереди на процессор или на диск! |
| **2** | `dmesg -T \| tail` | Ошибки железа, сбросы сети или **`Out of memory: Killed process`** (сработал OOM Killer!). |
| **3** | `vmstat 1` | `r` > ядер CPU (очередь на CPU), `si/so` > 0 (сервер ушёл в медленный swap!), `wa` высокий (CPU ждёт диск!). |
| **4** | `mpstat -P ALL 1` | Если 1 ядро загружено на 100%, а остальные 15 пустуют — однопоточное узкое горлышко (напр., Redis или прерывания NIC). |
| **5** | `pidstat 1` | Какой конкретно процесс (PID) прямо сейчас сжирает CPU или делает тысячи контекстных переключений. |
| **6** | `iostat -xz 1` | `%util` около `100%` и `await` десятки миллисекунд ➔ диск перегружен (ищи тяжёлые запросы БД или логирование). |
| **7** | `free -m` | Смотри колонку **`available`** (а не `free`!). Page Cache (`buff/cache`) в Linux — это норма. |
| **8** | `sar -n DEV 1` | Загрузка сетевых интерфейсов (rxkB/s, txkB/s) и дропы пакетов. |
| **9** | `ss -s` и `ss -lnt` | Количество сокетов в `TIME-WAIT`, `ESTAB`, и не растёт ли очередь `Recv-Q` (Accept Queue переполнена!). |
| **10** | `top` / `htop` | Общая картина процессов, потоков и состояний (`R`=Running, `D`=Uninterruptible I/O sleep, `Z`=Zombie). |

### Продвинутая отладка процессов и Go-сервисов:
```bash
lsof -p <PID>                   # Все открытые файлы и сетевые сокеты конкретного процесса
strace -c -p <PID>              # На какие системные вызовы (syscalls) процесс тратит время
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/profile?seconds=15  # Flamegraph CPU!
```

## 🐘 2. Шпаргалка по чтению `EXPLAIN (ANALYZE, BUFFERS)` в PostgreSQL

Всегда проверяй медленные SQL-запросы через `EXPLAIN (ANALYZE, BUFFERS) SELECT ...`:

| Что увидел в плане | Что это значит и как чинить |
| :--- | :--- |
| `Seq Scan on big_table` | База читает **всю таблицу построчно с диска**! Нужен B+Tree индекс (`CREATE INDEX CONCURRENTLY`) или переписать условие без функций над колонкой (`WHERE lower(email)` без функционального индекса убивает обычный индекс!). |
| `Index Only Scan` | **Идеал!** База достала все нужные поля прямо из индекса, даже не заходя в таблицу (Covering Index `INCLUDE`). |
| `Rows Removed by Filter: 950000` | Индекс плохо сужает выборку или неправильный порядок колонок в составном индексе `(a, b)`. |
| `Buffers: shared read=50000` | Пришлось идти на физический диск (не попало в Shared Buffers / RAM). |
| `Sort Method: external merge Disk` | Сортировка не влезла в `work_mem` и вывалилась на медленный диск! (Увеличить `work_mem` или добавить индекс для `ORDER BY`). |

### Оптимизация «пагинации» (Pagination) в High-Load:
- ❌ **Плохо:** `OFFSET 1000000 LIMIT 20` — база прочитает и выбросит 1,000,000 строк!
- ✅ **Хорошо (Keyset / Cursor Pagination):** `WHERE id > 1000000 ORDER BY id ASC LIMIT 20` — работает за мгновенные `O(log N)` на любой странице!

## 🛡️ 3. Сводная матрица паттернов отказоустойчивости (Resilience)

| Проблема в распределённой системе | Паттерн защиты | Как работает |
| :--- | :--- | :--- |
| Соседний сервис «подвис» и съел все горутины/потоки | **Timeout + Circuit Breaker** | Жёсткий дедлайн на вызов; при серии ошибок предохранитель переходит в `OPEN` и мгновенно рубит запросы на 30 сек |
| Миллион клиентов синхронно делают Retry и добивают базу | **Exponential Backoff + Full Jitter** | Задержка растёт как `2^n` плюс случайный сдвиг `random(0, exp)` |
| Сеть моргнула, клиент повторил оплату 2 раза | **Idempotency-Key + Transactional Outbox** | Повтор с тем же UUID-ключом возвращает кэшированный результат без повторного списания |
| Один «тяжёлый» клиент/поиск кладёт весь сервис | **Rate Limiting (Token Bucket) + Bulkhead** | Отсекаем лишний трафик (`429`) и изолируем пулы потоков/БД для разных критичных маршрутов |
| Протух горячий ключ в Redis и толпа пошла в БД | **Singleflight + Bloom Filter + Jitter TTL** | 1 запрос обновляет кэш, остальные ждут; несуществующие ID отсеивает Bloom Filter |
