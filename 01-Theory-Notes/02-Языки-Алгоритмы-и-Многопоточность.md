## 🛠️ 1. Языки Backend Systems Engineer (Без холиваров — по задачам)

1. **Go (Golang) — главный стандарт системного бэкенда и облаков:**
   - На нём написаны Docker, Kubernetes, etcd, Prometheus, Terraform, CockroachDB.
   - Причина: компилируется в 1 статический бинарник, быстрая сборка, встроенная модель **M:N горутин + каналов (`GMP`)**, отличное встроенное профилирование (`pprof`).
   - Главный нюанс: есть сборщик мусора (**Garbage Collector**), поэтому в экстремальном High-Load избегают лишних аллокаций в куче (`sync.Pool`, `Escape Analysis`).
2. **Rust — когда нельзя терпеть даже микросекундные паузы GC:**
   - На нём пишут современные хранилища, прокси (Pingora от Cloudflare, Vector, компоненты Firecracker), движки БД.
   - Нет сборщика мусора: память освобождается на этапе компиляции через систему владения (**Ownership & Borrowing**), а ошибки Data Race ловятся компилятором!
3. **Python — быстрая разработка, ML-сервисы и автоматизация:**
   - Отлично подходит для оркестрации, скриптов, прототипирования систем и FastAPI.
   - Системное ограничение: **GIL (Global Interpreter Lock)** не даёт двум CPU-потокам одного процесса выполняться параллельно на 2 ядрах (но I/O через `asyncio` или распараллеливание через `multiprocessing` работают!).

## 🔀 2. Модели конкурентности: Почему потоки ОС не тянут 100,000 клиентов

| Модель | Как работает | Цена 1 задачи | Когда ломается |
| :--- | :--- | :---: | :--- |
| **OS Threads (1:1)** | Каждый запрос обслуживается реальным потоком ядра Linux | **~1–8 МБ RAM** на стек + дорогой **Context Switch** | При 10,000 потоках сервер тратит секунды только на переключение регистров CPU и падает по RAM |
| **Single-Thread Event Loop** | 1 цикл на ядро крутит `epoll` (Nginx, Redis, Node.js, `asyncio`) | **~несколько КБ** | Если в обработчике сделать тяжелое вычисление на 200 мс (или синхронный вызов БД) — замирают ВСЕ 10,000 клиентов! |
| **M:N Scheduler (Go Goroutines / Rust Tokio)** | Миллионы лёгких задач (M) планируются поверх пула из N потоков ядра (обычно по числу ядер CPU) | **~2 КБ RAM** стартовый стек горутины! | Если забывать закрывать горутины через `context.Context` — будет **Goroutine Leak** (утечка памяти до OOM!) |

### Как работает планировщик Go (`G-M-P` модель):
- **G (Goroutine):** лёгкая задача со своим маленьким стеком (растёт динамически от 2 КБ).
- **M (Machine):** реальный поток операционной системы (OS Thread).
- **P (Processor):** логический контекст выполнения с локальной очередью горутин (число `P = GOMAXPROCS`, равно числу ядер CPU).
- Когда горутина `G` ждёт сеть (`netpoller` / `epoll`), она убирается с потока `M`, и поток тут же выполняет другую `G` (а если локальная очередь пуста — ворует задачи у соседнего `P`, это **Work Stealing**!).

## 🔒 3. Синхронизация и Ловушки Памяти в Многопоточности

1. **Data Race (Гонка данных):** два потока одновременно читают и пишут одну ячейку памяти без синхронизации ➔ непредсказуемое повреждение данных. В Go всегда гоняй тесты с флагом **`go test -race ./...`**!
2. **Mutex vs RWMutex vs Atomics (`CAS`):**
   - `Mutex` — эксклюзивный замок: внутрь критической секции входит ровно 1 поток.
   - `RWMutex` — много читателей одновременно ИЛИ 1 писатель. Полезен, когда 99% операций — чтение!
   - `Atomics` (`Compare-And-Swap`, `atomic.AddInt64`) — аппаратная инструкция процессора без блокировки потока ядром (Lock-Free). Для простых счётчиков в десятки раз быстрее мьютекса!
3. **Deadlock (Взаимная блокировка):** Поток A держит замок `M1` и ждёт `M2`; Поток B держит `M2` и ждёт `M1`. **Лечение:** всегда брать мьютексы в строго одинаковом глобальном порядке!
4. **Lock Contention (Давка у двери):** если повесить 1 глобальный `Mutex` на горячий кэш из 64 ядер, 63 ядра будут стоять в очереди. **Лечение — Sharded Map:** разбей кэш на 64/256 бакетов со своим мьютексом на каждый!
5. **False Sharing (Ложное разделение кэш-линий):** CPU читает RAM не по 1 байту, а **кэш-линиями по 64 байта**. Если два независимых счётчика для разных ядер лежат в соседних байтах одной кэш-линии, ядра будут постоянно сбрасывать кэш друг другу! Лечится выравниванием (*cache line padding*).

## 🧩 4. Системные структуры данных, которые реально используют в продакшне

| Структура | Как устроена на пальцах | Где применяется в реальном бэкенде |
| :--- | :--- | :--- |
| **Ring Buffer** | Массив фиксированного размера, где индексы чтения/записи бегают по кругу без аллокаций в куче | Сетевые драйверы (NIC), `io_uring`, очереди логов, **LMAX Disruptor** (биржевой движок с миллионом транзакций/сек) |
| **LRU / LFU Cache** | HashMap ($O(1)$ поиск) + двусвязный список ($O(1)$ перестановка горячих элементов) | Кэш в памяти приложения, **Redis Eviction** (`allkeys-lru` / `allkeys-lfu`) |
| **Bloom Filter** | Компактный битовый массив + $k$ хэш-функций. Отвечает: *«Точно НЕТ»* (100%) или *«Возможно ДА»* (с ложными срабатываниями ~1%) | **RocksDB / Cassandra** (не лезть на диск за несуществующим ключом!), защита Redis от **Cache Penetration** |
| **Skip List** | Многоуровневый связный список с «экспресс-линиями» ($O(\log N)$ поиск, прост в блокировках) | **Redis Sorted Sets (`ZSET`)**, `MemTable` в LSM-движках |
| **Token Bucket** | «Ведро» вместимостью $B$, куда капают токены со скоростью $R$ в сек. Разрешает короткие всплески (Burst)! | API Gateway **Rate Limiting** (Nginx, Envoy, Cloudflare) |
